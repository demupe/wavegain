ReplayGain filter investigation and SIMD implementation
Date: 2026-10-14 (Asia/Tokyo)
Baseline: 3fe2589 (historical filter investigation used 74e50db)
Host: macOS arm64; x86_64 validation ran under Rosetta.

88.2 kHz root cause
------------------
Both existing IIR denominators are mathematically unstable, independently of
SIMD, compiler contraction and input PCM width. The stored Yule denominator has
a real pole at approximately 1.4259220682, and the Butterworth denominator has
one at 1.0669839896. A pole magnitude greater than one makes a bounded impulse
response grow exponentially. For both polynomials P(1) is negative while the
leading coefficient is positive, proving at least one real pole above one.
Bisection locates the poles; Schur recursion also rejects both denominators.

The earliest available imported version containing these coefficients is
1.3.0 (bff3cf0); imported 1.3.1 has the same values. The existing 88.2 kHz last
Yule denominator term and last Butterworth denominator term repeat values from
the 64 kHz row. That suggests a copying error, but the original coefficient
creation process is not in the available history. Changing one guessed term
would not establish the intended frequency response.

Only the 88.2 kHz Yule and Butterworth rows were replaced with the published
FFmpeg coefficients, including the legacy SSE2 layout. The independent source
is FFmpeg libavfilter/af_replaygain.c, freqinfos[88200], read on 2026-10-14:
https://github.com/FFmpeg/FFmpeg/blob/master/libavfilter/af_replaygain.c
The numerator and denominator now form a documented, stable weighting filter.
All twelve rates pass Schur stability checks. Scalar and legacy table layouts
are checked for matching coefficients. Native filtering arithmetic, window
sizes, calibration constants and all other coefficient rows are retained.

Non-finite RMS levels now return GAIN_ANALYSIS_ERROR before integer conversion;
finite histogram levels are clamped before casting too. Previously a NaN from
the divergent filter reached an undefined floating-to-integer cast. This guard
reports an analysis failure; it does not turn non-finite samples into silence.
Callers must reset or stop after an analysis error, as the CLI already does.

Legacy SSE2 defect
------------------
The historical HAVE_SSE2 Yule kernel combines pairs of feedforward terms b0..b9
then adds input[-10] * kernel[11]. In its packed coefficient layout kernel[10]
is b10 and kernel[11] is padding zero, so the last feedforward tap was omitted.
The tap is corrected to kernel[10]. The separate legacy SSE2 arithmetic and RMS
summation remain as before. This branch is used by the existing Windows project;
it is separate from the new paired-channel SIMD implementation.

A dedicated x86_64 Clang probe compiled with HAVE_SSE2 and -fdeclspec reproduces
the old defect, then passes after correction. All twelve impulse/DC/tone
responses agree with an independent long-double recurrence within 1e-8; the
observed maximum Yule error is about 9.9e-12. Non-finite API input guards are also
checked. A full legacy-SSE2 CLI passes the independent 88.2 kHz conversion and
FFmpeg checks. This exercises the legacy code under macOS, not Windows/MSVC.

SIMD numerical policy
---------------------
Two binary64 vector lanes contain independent left/right samples. Time samples
are not split into independent lanes: each channel keeps the existing causal
IIR history. The two unrolled filter expressions keep the scalar operator order,
initial 1e-10 bias, coefficient selection and per-operation binary64 precision.
RMS accumulation, histogram construction and state movement are unchanged.

The loop-based investigation prototype first calculated input * b0 and then
added the Yule bias in another statement. Whether a compiler fused such
multiply/add pairs (FP contraction) depended on the compiler, version, target
ISA and even the statement layout, so scalar and vector kernels could differ.
The four filter functions (scalar and paired Yule/Butterworth) are therefore
compiled with contraction disabled: "#pragma GCC optimize" for GCC (kept per
function through LTO) and "#pragma clang fp contract(off)" for Clang. MSVC does
not contract under its default /fp:precise model. Every product and sum is then
rounded as written, so the paired path performs exactly the same IEEE binary64
operations as the scalar path on every compiler. The rest of the program
(gain, dither, limiter) keeps the compiler's normal floating-point policy.
Clang's scoped contraction controls are documented here:
https://clang.llvm.org/docs/LanguageExtensions.html#extensions-to-specify-floating-point-flags

The paired path is enabled by default for Clang and GCC 5 or later on AArch64
and on x86_64 with SSE2, without fast-math, and without the legacy HAVE_SSE2
implementation. No particular compiler version or AVX2/FMA level is required.
Only stereo takes this path; mono and legacy HAVE_SSE2 retain their existing
filtering paths. Fast-math always disables the paired implementation,
including explicit opt-in.

Because filter contraction is now disabled, builds for FMA-capable targets
(for example AArch64, or x86_64 with -march=x86-64-v3) differ in the last bits
of the filter state from earlier builds that let the compiler fuse operations.
At any sample rate this can move a gain that lies close to a 0.01 dB histogram
step by one step (observed: -0.44 dB -> -0.45 dB at 48 kHz). This is an
intended change. Targets that cannot use FMA (for example the default x86_64
-O2) are unaffected. The guarantee is bitwise scalar/SIMD equality within one
build; equality across compilers or ISAs is only established for the tested
configurations, because RMS accumulation and log10 keep the compiler's normal
floating-point policy.

make verified-release compares all-rate kernel/API state plus complete CLI
output against a scalar build using the same release/compiler/linker flags.
Unsupported target instructions (for example AVX-512 code on a CPU without
AVX-512) or any mismatch fail the build and remove the binary. VERIFY_SIMD
selects the backend requirement: auto (default) accepts either backend once it
matches the scalar reference, 1 requires the paired SIMD backend and never
accepts a scalar fallback, and 0 requires scalar. WAVEGAIN_FILTER_SIMD=0
remains an explicit scalar build; WAVEGAIN_FILTER_SIMD=1 cannot enable
unsupported compiler families/architectures.

Correctness validation
----------------------
The C probes compare scalar and paired Yule/Butterworth outputs bit-for-bit for
all twelve rates. Signals include silence, impulses, DC, alternating full scale,
deterministic random noise, distinct-channel tones, very quiet tones and chirps.
Calls include single-sample and irregular chunk boundaries. Public API tests
compare prehistories, partial-window sums, histograms, track/album gains and
reset state for mono/stereo and several chunk patterns (including window +/-1).
Actual histogram-bin transitions are located by bisection and tested at adjacent
double amplitudes and tiny level offsets. Invalid samples/energy overflow are
rejected under address, undefined-behavior and float-cast-overflow sanitizers.

Clang 21 arm64 and x86_64 default SIMD match their corrected scalar references
byte-for-byte. The eleven unaffected rates also matched prior 3fe2589 internal
state/histograms/gains before filter contraction was disabled. Since then, a
prior-revision comparison is expected to match only on targets that cannot use
FMA (verified: Clang -O2 -arch x86_64 and GCC 14 x86_64 -O2 against 219825c);
on FMA-capable targets such as arm64 it reports the intended difference.
Additional Clang -O3 and -ffp-contract=off probes pass. Historical loop-prototype
results are kept as separate evidence; they are not the production validation.

make check and make check-interop pass on arm64 with a full AddressSanitizer CLI
and on x86_64. Checks include existing PCM, sparse large-file WAV/Wave64, TODO,
progress, help, stdin/stdout and FFmpeg interoperability regressions.
The new independent 88.2 kHz test covers mono/stereo, four tones, WAV/Wave64,
five output sample formats and undo. FFmpeg gain differences are 0.01-0.02 dB.
Exact FFmpeg equality is not required: its float filter history, RMS scaling and
64.54 reference differ from WaveGain's binary64 history and 64.82 reference.

Performance
-----------
Sixty seconds of stereo 96 kHz input, Clang 21 -O2, five randomized interleaved
runs after a warmup, warm filesystem cache and file output included. Baseline
is 3fe2589, after the safe-buffer/float work, so this isolates the new filters.
Complete output bytes match in all six workloads.

Case          Old seconds New seconds Throughput  Bytes equal
calculate24   0.438253  0.269883  1.624x   True
apply16       0.500628  0.332885  1.504x   True
apply24       0.506144  0.363272  1.393x   True
float24       0.496572  0.332768  1.492x   True
dither24      0.749183  0.580074  1.292x   True
limiter24     0.558493  0.375735  1.486x   True

The ordinary apply cases improve by about 1.4-1.5x, calculation by about 1.6x,
and noise-shaped dither / limiter workloads by about 1.3x / 1.5x in this test.
These are synthetic warm-cache measurements on this host, not a universal speed
promise. Cold storage, mono, other rates and large Wave64 storage throughput
have not been benchmarked. RMS/dither/limiter still limit some workloads.

Reproduction and evidence
-------------------------
make check
make check-interop                         # requires FFmpeg / ffprobe
python3 tools/check_filter_stability.py --output /tmp/filter-stability.json
python3 test/filter_regressions.py --output /tmp/filter-equivalence.json
# Prior-revision compatibility: compare on a target without FMA. On FMA-capable
# targets (arm64, -march=x86-64-v3) the intended filter rounding change fails it.
python3 test/filter_regressions.py --cflags='-O2 -arch x86_64' \
    --reference-ref 3fe2589 --output /tmp/filter-equivalence-x86.json
python3 test/filter_regressions.py --cc gcc-16
python3 test/filter_regressions.py \
    --cflags='-O2 -fsanitize=address,undefined,float-cast-overflow -fno-sanitize-recover=all'

    --variants baseline,working_tree --output /tmp/filter-performance.json
python3 test/filter_interop.py --output /tmp/filter-88200-interop.json

Verify automatic selection for a compiler and flag set with, for example:
python3 test/filter_regressions.py --cc gcc \
    --cflags='-O2 -fPIC -flto -march=x86-64-v3' --ldflags='-flto -lm' --expect-simd 1
Use --expect-simd 1 with the actual build flags on a compatible CPU. The
expectation fails at compile time if the paired path is unavailable, so comparing two scalar runs cannot silently certify SIMD.
Build and verify together: make verified-release CC=gcc VERIFY_SIMD=1 \
    CFLAGS='-O2 -fPIC -flto -march=x86-64-v4' LDFLAGS='-flto'
This also checks the built CLI's output against a scalar CLI for 44.1/48/88.2
kHz, mono/stereo and with/without DC correction (twelve conversion cases).
Run make install only after verified-release succeeds.
Environment CC and LDFLAGS are now honored by the Makefile.

Force scalar CLI: make release CPPFLAGS='-D_FILE_OFFSET_BITS=64 -DWAVEGAIN_FILTER_SIMD=0'
Historical prototype: tools/check_filter_equivalence.py defaults to --ref 74e50db.

Evidence files: filter-stability.json, filter-equivalence-{arm64,x86_64,gcc,
sanitize,x86-sanitize}.json, filter-88200-{interop,legacy-interop}.json and
filter-performance.json. Future validation remains for native Windows/MSVC,
additional Linux targets and compiler versions/options. Unsafe fast-math builds
and cross-compiler bitwise equivalence are not part of the validated contract.
