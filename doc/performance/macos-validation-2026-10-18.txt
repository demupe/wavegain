Native macOS validation and v1.5.0 comparison
Date: 2026-10-18 (Asia/Tokyo)
Reference: v1.5.0 / 628ce4211e705eae958f96cddf5c3951b1265dce
Candidate: perf/verified-pcm-optimization / de0a68a41086c93c7c1a88bb4f842e29868bc1d6

Outcome
-------
The branch improves default ReplayGain throughput on this Apple M1 Pro.
Default O2 apply is 1.385..2.208x faster in the six mono/stereo cases
(about 28..55% less elapsed time). Matched O2 comparisons isolate the
branch changes from compiler tuning.
All core, sanitizer and FFmpeg interoperability checks pass. Both default
and O3/ThinLTO candidates preserve the complete output bytes of v1.5.0
O2 across 1,260 normal-input cases each. Three targeted before/after
probes also confirm safer rejection while retaining the original input.

Changes reviewed
----------------
* Integer PCM decode selects width/byte order once per block; plain
  integer gain uses a dedicated no-dither/no-limiter quantizer path.
* Mono ReplayGain reuses identical filters until stereo history appears.
* AArch64 stereo ReplayGain keeps paired IIR histories and fuses stages;
  local peak/DC accumulators retain the original summation order.
* Mirrored high-rate FIR history removes per-tap ring wrap branches.
* Safety changes validate undo scales, partial frames and extensible
  precision, retain input identities to prevent repeated processing,
  and avoid narrowing large DC displays. Windows-only changes bound
  commands, fix diagnostics and resolve recursive/output path aliases.
* Shared test inventory, strict rejection checks and coverage expanded.
No production code or default compiler flags were changed by this review.

Host and method
---------------
MacBook Pro (MacBookPro18,3), Apple M1 Pro: 6 performance + 2 efficiency
cores, 32 GiB RAM; macOS 26.7.1 (25G241), native arm64, AC power.
Apple clang 21.0.0 (clang-2100.3.34.2); Python 3.15.0; FFmpeg 9.0.2.
Reference and O3 candidate sources came from clean git archives. The O2
candidate used the initially clean working tree at the recorded commit.
Flags match within each O2 or O3/ThinLTO comparison. No fast-math.
Reference Makefile
does not expose RELEASE_OPT, so its O3 flags were supplied to CFLAGS.
One warm-up followed by five repetitions per executable, alternating
execution order. Tables show median wall seconds and reference/candidate
ratios. Launch, reads and output writes/replacement are timed; input
restoration and complete-file SHA-256 are outside the timer. OS caches
are warm and storage flushes are not forced. All repetitions are retained;
no outliers are discarded. Some apply runs show substantial I/O or OS
variation (up to 68% min-to-max/median in an O2 candidate case), so use
the medians and inspect raw samples rather than treating one run as exact.
Validation/build jobs had finished before timings; benchmark jobs ran
sequentially.

Synthetic seeded tones + noise use tools/benchmark_native.py fixture().
44.1 kHz/16-bit and 96 kHz/24-bit inputs are 180 s; 192 kHz/24-bit is
60 s. Stereo channels differ. Mono takes the left channel of each
stereo fixture. The generated one-second pattern repeats. Input hashes,
all repetitions, binary hashes and final apply-output hashes are in the
paired JSON. Analysis-only benchmark hashes are empty, so equality for
analysis relies on the separate filter-state and differential tests.

Correctness and safety
----------------------
* Core: debug, default O2 and O3/ThinLTO each pass all 15 Mac-applicable
  groups; four Windows-only groups explicitly skip. The final O2 run
  supplies O2 to the C probes as well as to the application.
* ASan + UBSan + float-cast-overflow: all 15 groups pass with
  halt_on_error=1. No sanitizer error was observed.
* verified-release at O2 and O3/ThinLTO: scalar/default filter API
  state, histories and histograms agree bit-for-bit across 12 rates;
  12 scalar/actual CLI conversions match. Loudness kernels match the
  reference at all 14 rates, including irregular blocks and gating.
* FFmpeg: all four interop groups pass: Wave64; 88.2 kHz filters and
  format conversion/undo; RIFF/RF64; LUFS/true peak at 44.1..192 kHz
  with frame/rate preservation and quantized output peak ceilings.
* Differential: v1.5.0 O2 vs branch O2, and v1.5.0 O2 vs branch
  O3/ThinLTO: 1,260 complete output matches each. Seven rates, mono/
  stereo, integer 8/16/24/32 and float32, 18 option combinations.
  Includes DC/gain, album, dither, limiter, LUFS/true peak, RF64,
  gain metadata and five output formats. Source bytes stay intact.
* Every benchmark apply-output hash matches its paired reference.
* Partial-frame, invalid-valid-bits and duplicate-path probes:
  v1.5.0 returns success and changes the input; branch returns 1 and
  preserves the original bytes in all three. See safety_comparison.
* Debug emits the same single invalid-UTF-8 license-comment warning
  as v1.5.0. The original license bytes were retained. Release linker
  warns that -s is obsolete, and some probes report unused -s;
  these warnings do not fail validation.

Scope and remaining work
------------------------
These are short, synthetic, warm-cache, single-file observations on
one Apple Silicon host, with no confidence intervals. They do not
establish real-music, cold/storage-bound, multi-file scaling or Intel
Mac performance. LUFS/true-peak and dither can dominate their own modes;
use their measured rows rather than extrapolating ReplayGain ratios.
No audible-quality improvement is claimed: normal output is preserved.
Official EBU conformance signals, Linux, native GCC/MSVC, hardware x64,
real ACL/SMB/cloud behavior and perceptual dither remain unvalidated.
Windows-only tests are skipped here; previous Windows reports retain
their original scope. No claim that every latent defect is excluded.

Reproduction
------------
1. Export v1.5.0 and the candidate commit into separate directories:
     git archive v1.5.0 | tar -x -C /tmp/wg-reference
     git archive de0a68a | tar -x -C /tmp/wg-candidate
   Create directories first. Keep binaries outside the source trees
   before make clean/rebuild. Use the compiler/macros recorded above.
2. Reference: make release CC=clang; copy the binary as reference-o2.
   For O3: make clean; make wavegain CC=clang
     CFLAGS="-s -O3 -flto=thin -D_FORTIFY_SOURCE=2"
3. Candidate: make debug; make check; make check-sanitize CC=clang;
     make verified-release CC=clang; make check-interop
   For optimized builds: make verified-release CC=clang
     RELEASE_OPT=-O3 LTO_FLAGS=-flto=thin
     make check CC=clang CFLAGS="-O3 -flto=thin -D_FORTIFY_SOURCE=2"
4. Run test/pcm_equivalence.py --reference reference-o2
     --candidate candidate-o2 --output equality.json
   Repeat with candidate-o3. Use absolute executable paths.
5. Generate stereo fixtures with benchmark_native.fixture(path, rate,
   bits, seconds), using (44100,16,180), (96000,24,180), (192000,24,60).
   Extract each left channel without resampling for the mono fixtures.
6. Run tools/benchmark_native.py --reference reference-o2
     --candidate candidate-o2 --runs 5 --output timings.json
     --input input.wav [repeat --input for each of the six fixtures]
   Repeat with both O3 binaries. For extra modes, extract the paired
   JSON supplementary_benchmark_source into a Python file and pass
   only the 96 kHz stereo fixture with the same arguments.

Repository final application is restored to the ordinary O2 release;
only validation evidence, the documentation index and status notes
are changed. No release/version bump or commit is created.
