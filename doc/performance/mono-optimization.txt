Exact mono ReplayGain optimization (2026-10-17; base 31cf06a)
===========================================================

The original mono analysis feeds the same samples through both channel
filters, starting with identical histories. Compute the left Yule and
Butterworth outputs once and copy each output to the right channel. Both
channels retain their original input and output histories, RMS arithmetic,
histograms and gain selection. No coefficients or arithmetic order change.
memcpy operates on distinct arrays, bounded by the existing RMS-window
batching. It also preserves the bit patterns of the computed samples.

AnalyzeSamples is a public API and can switch channel counts mid-track.
After any nonempty stereo call, reuse stays disabled until a successful
ResetSampleFrequency or GetTitleGain clears the histories. Comparing only
the current input pointers would be incorrect after stereo IIR histories
have diverged. WAVEGAIN_MONO_REUSE=0 selects the original calculation for
verification; it is a compile-time test control, not a new CLI option.

Verification
------------
test/filter_regressions.py disables both paired SIMD and mono reuse in its
reference build, including the CLI output comparison. The default build
must match every byte of the private-state probe, not just rounded gains.
New cases cover all twelve filter rates, mono/stereo/mono transitions,
small chunks, partial/full RMS windows, title/album resets and explicit
frequency resets after stereo input. Existing signals and non-finite
guards remain in the comparison. The ARM64 state probe emits 47,829,181
bytes. On x64 Clang, the historical HAVE_SSE2 backend is also built with
reuse off/on and its complete state/histogram output must match. This
extends the former legacy-backend impulse/DC/tone checks to mixed-channel
API sequences, resets and mono non-finite input as well.

ARM64 and Windows-emulated x64 full regression gates, the prior/current
1,260-case complete audio-file comparison, and ARM64 UBSan filter checks
are run for this change. See mono-performance-windows.json for results.
FFmpeg interoperability, native MSVC/GCC, macOS/Linux, and hardware x64
performance remain outside this Windows ARM64 validation.

Performance and rejected experiment
-----------------------------------
Windows 11 ARM64, Snapdragon X Plus, LLVM-MinGW Clang 23.1.1. Both binaries
use identical flags. The O3/ThinLTO reference is the preceding branch build
31cf06a. Measurements use synthetic 180-second 44.1 kHz/16-bit WAVs, one
warm-up and medians of five alternating runs; copying/hashing is excluded
from timing. Apply includes analysis, conversion and file I/O; complete
output files match. Warm OS caches and short process times limit the scope
of the results; these are incremental gains, not a v1.3.2 comparison.

O3/ThinLTO mono analysis: 0.4360 -> 0.2497 s (1.746x).
O3/ThinLTO mono apply:    0.4901 -> 0.3040 s (1.612x).
Stereo controls: 1.002x analysis and 0.988x apply; no stereo speedup claimed.
Default O2 mono analysis: 0.4350 -> 0.2470 s (1.761x).
Default O2 mono apply:    0.4959 -> 0.3069 s (1.616x).
O2 stereo controls: 1.000x analysis and 1.007x apply.
The optimization concerns ReplayGain filters; it does not speed up the
separate LUFS measurement engine.

A further prototype skipped right-channel RMS summation while mono
histories were identical. Full filter state still matched, but measured
mono analysis/apply ratios were 0.979x/0.990x relative to filter reuse alone.
Stereo controls were 0.992x/0.989x. This prototype was removed: the extra
conditions did not produce a useful gain. Its raw timings are retained.
