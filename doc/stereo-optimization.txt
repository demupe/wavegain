Exact stereo analysis optimization (2026-10-18; base 8a9a9f7)
===========================================================

Two changes address the common stereo ReplayGain analysis path.

1. Paired filter histories and stage fusion on AArch64
----------------------------------------------------
The former paired SIMD implementation reconstructs stereo vectors from
planar input/output histories at every sample, then scans all first-stage
output again through the second filter. The new implementation loads ten
paired input histories, ten paired Yule histories and two Butterworth
histories at the start of a chunk. Local vectors advance with each sample;
the Butterworth stage consumes each Yule result immediately.

Both stages keep exactly the original expressions, parentheses and
rounding. FP contraction remains disabled. Intermediate Yule results and
final results still go into the same planar arrays, preserving histories
across caller chunks and RMS windows. Coefficients, histogram/RMS energy
calculation, gain selection and output quantization do not change. Mono
continues to use the previous exact mono-reuse implementation.

Keeping so many histories live increases vector-register pressure. Enable
this path by default only on AArch64. The x64 emulation experiment became
substantially slower when forced to use it; x64 retains the former paired
two-pass path. WAVEGAIN_STEREO_HISTORY=0 retains that path on AArch64 too,
and =1 can force the new path for investigation. This compile-time control
has no CLI option. Existing scalar and historical HAVE_SSE2 paths remain.

2. Peak/DC scan accumulators
---------------------------
For each channel and input block, keep the minimum, maximum and DC sum in
local variables and store them back after the scan. The previous inner
loop repeatedly updated objects accessible through other pointers. This
change gives the compiler local accumulator dependencies without adding
restrict contracts or changing the order of operations. Scaling and
non-finite validation stay in the same scan; input rejection remains.

On targets whose FLT_EVAL_METHOD is nonzero or unavailable, make the local
DC sum volatile to preserve each legacy binary64 store/rounding point.
Tested ARM64/x64 targets use ordinary double evaluation and do not need
those extra stores. DC summation is sequential; there is no reassociation,
parallel reduction or change to fast-mode DC behavior. The scan improvement
also applies to mono and LUFS, although throughput figures below concern
ordinary stereo ReplayGain, without extra dither or true-peak processing.

Verification and limits
-----------------------
test/filter_regressions.c compares the combined paired kernel directly
with the two scalar kernels for all twelve rates and eight signal patterns.
Chunk lengths include one sample and history/window boundaries. It checks
every intermediate and final sample, then compares API histories, energy,
histograms, gain boundaries, mono/stereo transitions, resets and non-finite
guards. The compiler-selected default is compared with a scalar reference
with mono reuse disabled. The former paired path is also checked explicitly.

The 1,260-case O2 prior/current CLI comparison covers integer/float PCM,
mono/stereo, seven rates from 8 to 192 kHz, dither, gain, DC, LUFS, true peak,
bit depths and output containers. Entire generated files must match.
ARM64 UBSan filter checks and ARM64/x64 full Windows gates are included.
The debug build adds no warnings; the original non-UTF-8 license comment
still generates its existing warning and is retained byte-for-byte.

Tests ran on Windows ARM64 with LLVM-MinGW Clang 23.1.1; x64 execution uses
Windows emulation, not native hardware. Native MSVC/GCC, x64 hardware,
macOS/Linux, x87 and FFmpeg interoperability are not validated here.

Measurement and experiments
---------------------------
See stereo-performance-windows.json for raw timings, binary hashes, output
hashes and verification records. The comparison is incremental from branch
commit 8a9a9f7, not from v1.3.2. Both binaries use matching compiler flags.
Benchmarks use synthetic 180-second stereo WAVs: 44.1 kHz/16-bit and
96 kHz/24-bit, one warm-up and five alternating runs. Wall-clock medians
include process launch and I/O, with copying/hashing outside the timer and
warm OS caches. The benchmark verifies complete apply-output hashes.
These short warm-cache tests do not establish cold-storage or real-music
throughput, and gains will depend on dither, metering and source formats.

Final medians (seconds; analysis / apply):

ARM64 O3/ThinLTO:
  44.1 kHz/16-bit: 0.2759 -> 0.2154 (1.281x) / 0.3650 -> 0.3065 (1.191x)
  96 kHz/24-bit:   0.5890 -> 0.4493 (1.311x) / 0.7701 -> 0.6286 (1.225x)
ARM64 O2:
  44.1 kHz/16-bit: 0.2858 -> 0.2275 (1.256x) / 0.3728 -> 0.3102 (1.202x)
  96 kHz/24-bit:   0.5979 -> 0.4563 (1.310x) / 0.7898 -> 0.6501 (1.215x)
Emulated x64 O3/ThinLTO (scan improvement only):
  44.1 kHz/16-bit: 0.3306 -> 0.2863 (1.155x) / 0.4434 -> 0.3986 (1.112x)
  96 kHz/24-bit:   0.6925 -> 0.5989 (1.156x) / 0.9570 -> 0.8553 (1.119x)

Rejected/narrowed approaches:
* Adding restrict to the former paired kernels did not give a consistent
  gain and was removed. No new pointer-aliasing contract is imposed.
* Retaining only Yule output histories, and loading input histories each
  time, gave inconsistent changes around 1%; retain the full local history
  implementation on AArch64 instead.
* Forcing full history retention on emulated x64 was much slower. Preserve
  the former paired path on targets other than AArch64; keep the peak/DC
  scan improvement independent of this choice.
