1. Native 64-bit build: completed, stale TODO wording
---------------------------------------------------
History:
  4fce6df added test/outsox.wav for Issue #2.
  8f14080 forced -m32 as a workaround.
  4daa751 added the still-present investigation wording.
  8b224d3 fixed PCM widths and portable conversion and added Wave64 support.

24/32-bit output previously read an int buffer through long*. On LP64, long is
8 bytes while the PCM elements are 4 bytes. The writer thus skipped samples
and eventually read outside the intended buffer. The old x87 conversion also
wrote a 32-bit result into a long and was unsuitable for ARM builds. The source
now uses int32_t, standard lrint, large file offsets, unsigned chunk decoding
and 64-bit fast-mode seek positions. The Makefile no longer forces -m32.

Prior validation in this session: the old x86_64 source failed the exact PCM
byte comparison; the fixed source passed. Native arm64/x86_64 and ASan tests,
Issue #2 waveform comparison and sparse large-file tests passed. Existing
regression commands are make check and make check-interop (requires FFmpeg).

2. Progress: three confirmed defects
-----------------------------------
Source: wavegain.c/write_gains(), wavegain.c/get_gain(), main.c/process_files().

Actual measurements:
  0.5s, 44100Hz stereo: final file progress inf%, overall 100%.
  4.5s, 44100Hz stereo: final file progress 112%, overall 100%.
  4.5s at 8000Hz followed by 4.5s at 48000Hz: overall reaches 171%.

Per-file percentage divides the floating elapsed time by
(total_samples_per_channel / rate). Both denominator operands are integers.
A duration shorter than one second becomes zero; fractional seconds are lost.
For example 4.5 seconds becomes 4 seconds, so 4.5 / 4 * 100 = 112.5%.

Overall elapsed time is accumulated in seconds, but its denominator is the
sum of all analyzed frames divided by the current file's sample rate. Frames
at different rates cannot be converted into a duration using one rate. The
example has 252000 frames, and the second file's denominator is 5.25 seconds
rather than the actual 9 seconds. The throttling rule prints only while
floor(total_files) % 4 == 0, so the last displayed value need not be the true
final ratio. It also prints repeatedly within each qualifying second.

These are accounting defects; clamping the display to 100% alone would hide
them. Use processed_frames / declared_frames per file and independently sum
file durations for overall work. Handle unknown/zero lengths and mismatched
headers explicitly. Decide how skipped files affect the denominator. Emit a
final completion update and throttle using elapsed time since the last update.

Suggested regression matrix: 0.5s/4.5s, exact integer durations, mixed sample
rates in both orders, zero/unknown lengths, skipped tracks, WAV/Wave64/AIFF,
calculate/apply/undo and normal/album modes. Mixed-rate album analysis itself
also needs separate validation; this probe used the default track mode.

3. DC correction, manual gain and clipping: audio defect confirmed
----------------------------------------------------------------
Source: wavegain.c/get_gain(), wavegain.c/write_gains(), main.c/process_files().

Current order:
  Analyze original samples -> add manual dB -> cap gain using original peak
  -> subtract chosen DC -> multiply by selected scale -> optional tanh limiter
  -> quantize/dither -> clamp to the output sample range -> serialize PCM.

The clipping cap and New Peak are calculated from the uncorrected input peak,
whereas the written samples have their mean subtracted first. Subtracting a
positive mean can increase the magnitude of a negative excursion. The cap
therefore does not reliably prevent clipping with the default DC correction.

Fixture: one second, stereo 16-bit, 44100Hz; 0.3 DC plus a 0.01-amplitude 440Hz
sine, replaced by -0.55 at frames 0 and 22050. Input normalized peak is about
0.55 and the corrected peak about 0.85. The selected +5.19dB gain has a scale
about 1.82, taking the corrected peak to about 1.54 before limiting/clamping.
The negative pulses in both channels are clamped at -32768.

Measured CLI / output values:
  Options              Gain dB  New Peak   Output minimum  Rail samples
  default                 5.19     32765          -32768             4
  -g 12                   5.19     32765          -32768             4
  -g 12 -p                5.19     32765          -32766             0
  -g 12 -n               29.68    549275          -32768             4
  -g 12 -t                5.19     32765          -32275             0
  -g 12 -n -t            29.68    549275          -32768             4
  -a -q -g 12             5.19     32765          -32768             4

The album+ADC case here contains one track. It exercises that option path,
but does not validate the choice of a common DC value across different tracks.
The limiter's rail samples at very large gains are not by themselves proof of
hard clipping: tanh can round to its +/-1 asymptote in floating-point arithmetic.
The default case is conclusively clipped because its pre-clamp magnitude is
well above one and no limiter is enabled.

Manual gain addition itself works: an ordinary sine with -n -p reports -0.83dB,
and adding -g 6 reports +5.17dB (exact displayed difference +6.00dB). Both track
and album source paths add settings.man_gain once. A cap can intentionally make
-g 12 and no manual adjustment select the same final gain. This is distinct
from the incorrect DC peak used by that cap.

--noclip disables gain prevention; write_gains() still enforces representable
PCM/float limits. --limiter does not alter the gain recommendation or relax its
cap; it uses a smooth tanh knee at +/-0.5 after scaling. New Peak ignores both
DC correction and limiting and can therefore misdescribe actual output.

Proposed fix:
  Track per-channel minima, maxima, means and frame counts during analysis.
  After deciding the actual track/album DC subtraction, derive the peak from
  min/max minus that subtraction. Use that peak for the gain cap.
  Retain the raw peak as an explicitly separate diagnostic if desired.
  For album gain, compute the maximum corrected peak across all tracks after
  the common/per-track DC policy is known. Do not cap GetTitleGain using the
  wrong peak before that policy is selected.
  Define whether New Peak means pre-limiter predicted peak or actual measured
  written peak, and make the displayed field and help agree.
  Specify whether enabling the limiter should also change the gain cap; this
  is a behavior decision, not an automatically established bug fix.

Open tests: genuinely different two-track means, album and track DC policies,
manual gain at -20/+12, -p, -n, -t and combinations, all output widths, float,
dither and quantization headroom. Preserve loudness algorithm behavior unless
an additional experiment demonstrates a reason to change it.

4. --help, wildcards and documentation synchronization
-----------------------------------------------------
main.c/usage() prints version and copyright above Usage. The TODO asks for the
copyright to move to the bottom; no option parsing defect follows from this
placement. Quoted patterns are processed by recurse.c when ENABLE_RECURSIVE is
compiled. A literal manual*.wav argument finds the generated fixture in the
probe. POSIX shells may expand unquoted '*'/'?' before WaveGain runs, so help
should show a quoted example, e.g. wavegain '*.wav'. The matcher is case
sensitive on non-Windows builds and case insensitive on Windows. Linux runtime
behavior has not been executed in this investigation (the host is macOS).

There are four independent representations:
  main.c/usage(): CLI help, with conditional --exec and --recursive.
  README: copied help text.
  debian/wavegain.1: hand-authored nroff, dated October 17, 2012.
  doc/manual/index.html: independently maintained HTML.

CLI help and README now mention Wave64; man/HTML do not. Existing --fast text
also disagrees with implementation: the full-analysis threshold is 8192000
BYTES, and sampled analysis makes at most 200 calls of BUFFER_LEN=16384 frames
(each frame contains one sample per channel). The man page incorrectly says
it analyzes 8192000 samples. The threshold and actual read count must be
specified separately, rather than copied between documents as the same value.

Use one structured definition of options, descriptions and platform/build
conditions, plus shared explanatory sections, to emit CLI text, README text,
nroff and HTML. A check should compare generated files with committed files.
Keep GNU/Linux and Windows conditionals explicit; do not generate the universal
manual solely from a platform-limited binary without handling those omissions.
This design is proposed; no documentation generator or help layout was changed.

5. License/copyright header inventory: provenance still unresolved
-----------------------------------------------------------------
The repository-wide COPYING text is GNU Lesser GPL 2.1, and debian/copyright
labels upstream as LGPL-2.1+. The README records the maintainer's view that the
project as a whole should be LGPL-2.1+. File-specific notices still differ:

  audio.c/audio.h: GNU Library GPL version 2 or later, with several authors.
  gain_analysis.c/.h: LGPL 2.1 or later, Robinson/Sawyer and other contributors.
  getopt.c/getopt1.c/getopt.h: GNU Library GPL 2 or later, separate FSF notices.
  dither.c/.h: GNU Library GPL version 2; no explicit or-later wording in header.
  main.c/wavegain.c/misc.c/recurse.c: "GNU General Public License, version 2.1".
  config.h/i18n.h/main.h/misc.h/recurse.h/wavegain.h: no explicit header notice.
  w64.c and the new test sources: no explicit license/copyright notice.

The GNU license index lists GPL 1, 2 and 3 and LGPL 2.1 separately:
https://www.gnu.org/licenses/old-licenses/old-licenses.en.html
Thus the four "General Public License, version 2.1" notices are ambiguous;
the package-level COPYING cannot by itself prove the intended correction.
The same wording is already in the earliest imported source a0de6d1, so it was
not introduced by the recent native/Wave64 work. The dither header references
LICENSE.LGPL and GNU getopt references COPYING.LIB; neither file exists here.
Debian's GPL-3+ notice also has a text typo calling its GPL-3 location version 2.

Next work: preserve all existing authors and contributor notices; resolve the
four ambiguous notices against original release archives/author statements;
record each file's actual grant and or-later status; then add precise SPDX
identifiers, consistent attribution formatting and valid license-text links.
A package-wide replacement with one assumed SPDX license is not supported by
this inventory. This is a source/provenance inventory, not a relicensing action.
