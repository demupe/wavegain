WaveGain conversion performance investigation
Date: 2026-10-14 (Asia/Tokyo)
Source baseline: 74e50db
Host: macOS arm64, Apple clang 21.0.0

Outcome
-------
The largest measured opportunity is stereo ReplayGain filtering. A temporary
paired-channel vector prototype reduced typical full conversion wall time by
about 35% (approximately 1.5x throughput). Native float serialization gave about
5% end-to-end improvement on float output. Allocation reuse and simpler peak
comparisons did not show a substantial reliable improvement on this host.

At the time of this investigation, production conversion code had not been modified.
Subsequent safe changes and their measurements are documented separately in
conversion-safe-implementation.txt and conversion-safe-performance.json. Experiments are implemented
only by patching temporary source copies in tools/benchmark_conversion.py.
The prototype is not ready for production: numerical equivalence and platform
fallbacks need to be established, and existing correctness issues were found.

Method and scope
----------------
Six workloads, eight variants, one warmup per pair and five timed repetitions
in a deterministic shuffled order (240 timed runs). Each input is 60 seconds
of stereo 96 kHz audio, 5,760,000 frames / 11,520,000 channel samples. 16-bit
and 24-bit PCM files contain approximately 23 MB and 35 MB of audio respectively.
The channels are different sums of periodic sine waves with different DC values.

The baseline uses -O2 -D_FORTIFY_SOURCE=2 and the project's native 64-bit build
macros. Other compiler variants use -O3 and -O3 -flto. There is no fast-math.
Output is written to a temporary regular file using --stdout, so this measures
analysis plus gain application, conversion and file output. It does not time
in-place replacement, final seekable WAV header rewriting or permission copying.
The SHA-256 comparison includes the complete emitted stream (one warmup run
per case/variant), including the existing stdout header conventions.

Measurements use warm filesystem caches and include output writes. Whole-run
wall, user CPU and system CPU timings are recorded separately; wall medians,
min/max ranges and all repetitions are in conversion-performance.json. CPU
stage times use an independently instrumented binary, clock() around block
operations and medians of three runs. Those percentages are approximate and
should not be read as percentages of physical disk waiting time. Synthetic
inputs and a single host are insufficient to certify all material/platforms.

Candidates and tradeoffs
-----------------------
1. Pair the independent stereo IIR filters (largest measured gain).
   gain_analysis.c/AnalyzeSamples() calls filterYule() separately for left and
   right, then filterButter() separately. Each IIR depends on earlier samples,
   so vectorizing adjacent times requires a different recurrence. Left/right
   states, however, are independent and fit two double-precision vector lanes.
   The experiment keeps the filter coefficients, bias and history layout while
   advancing both channels together. Mono continues on the original scalar path.

   The existing HAVE_SSE2 implementation is not a drop-in portable switch: it
   has separate coefficient layouts, Intel intrinsics and MSVC-style alignment
   declarations, and its arithmetic grouping differs from the scalar path.
   A new NEON/SSE2/portable vector path would need explicit supported compiler
   and CPU guards, a scalar fallback and numerical acceptance tests.

   Direct comparison covers 196608 Yule/Butter output doubles across all 12
   coefficient sets using deterministic random inputs. Default ARM floating
   operation contraction produced bit differences in 174866 values. For stable
   coefficient sets, the largest absolute difference was about 1.4e-7 in the
   ReplayGain-scaled intermediate values (not normalized output audio).
   Even when rounded loudness or a gain cap hides such differences in final
   bytes, material near a histogram boundary may expose a gain difference.

   Compiling both paths with -ffp-contract=off made these intermediate outputs
   bit-identical, including matching non-finite patterns in the separately
   problematic 88.2kHz case. A separate five-run warm-cache 24-bit conversion
   check of this setting gave 0.470s scalar and 0.336s pair (~1.40x); emitted
   bytes matched. This follow-up ran the two variants sequentially, rather than
   the main benchmark's shuffled schedule; it is recorded separately in
   conversion-contract-performance.json. Changing contraction for the entire
   program could affect existing results elsewhere, so a production solution
   should make the scalar/vector filter policy explicit and verify it directly.

2. Serialize IEEE binary32 from its bit representation (small but useful gain).
   audio.c/write_audio_float() allocates a buffer, calls frexp() for every
   sample and reconstructs the bytes using exponent/mantissa arithmetic.
   Float input already uses native float storage, making bit-based serialization
   a natural counterpart. The little-endian IEEE host prototype writes native
   floats directly, normalizing signed zero to match existing output.
   End-to-end float output improved 0.524s -> 0.498s (~1.05x).
   The combined filter/float/buffer/stats prototype reached 0.320s (~1.64x).

   Use memcpy to/from uint32_t for portable bit access; verify binary32 properties,
   preserve explicit WAV little endian on other hosts and define signed-zero
   compatibility. Existing subnormal handling is incorrect (see below), so a
   correct writer cannot match all legacy output bytes. That difference should
   be tested and documented as a bug fix rather than silently accepted.

3. Reuse buffers / reduce copies (good structural cleanup, small measured gain).
   write_gains() allocates an oversized sizeof(double) * channels * frames
   intermediate each block. output_to_PCM() casts/reinterleaves it, and each
   write_audio_*() allocates another buffer, packs bytes, writes and frees it.
   At 60s/96kHz there are 352 non-empty blocks: two allocation/free pairs per
   block, roughly 704 pairs per file, despite fixed maximum buffer sizes.
   Reusing one PCM buffer and one serializer scratch buffer avoids those pairs.

   The experiment's medians changed by about -2% to +2%; the output writer's
   1-2% CPU share explains why this does not materially speed up the full path.
   Native-endian 16/32-bit direct writes and fused quantization/interleaving/
   packing could remove more copies, but were not separately benchmarked here.
   They require exact rounding/clipping/dither-sequence compatibility and endian
   fallbacks. Allocation failure and I/O error handling must also be preserved.

4. Specialize dither/limiter dispatch and investigate shaping independently.
   Each sample rechecks DC/ADC, limiter, format, dithering and shaping flags.
   Hoist stable choices outside the sample loop, select one kernel per file,
   and consider a dedicated no-dither/no-limiter loop. These are source-level
   opportunities, not measured speedups in this investigation.

   With noise shaping, dither_output() invokes scalar16() twice per sample,
   maintains per-channel error histories and advances a shared RNG. A reduction
   using a different summation order or reordered channel processing can alter
   dither bytes. Preserve the RNG call sequence, history phase, rounding and
   arithmetic precision if output compatibility is required. Parallelizing
   files requires moving Dither, doubletmp and the RNG into per-job state.

5. Compiler flags / peak-statistics comparisons (limited gains).
   -O3/-flto were roughly 1-5% faster in some whole-pipeline cases, with weak or
   negative wall-time changes elsewhere. They are not a substitute for changing
   the dominant algorithm organization. All measured workload bytes matched,
   but broader tests and other toolchains would still be needed.
   Replacing fmin/fmax with finite-value comparisons in analysis showed no
   reliable material improvement. Keep the non-finite input validation intact.
   -ffast-math was not tested or recommended: the code intentionally rejects
   non-finite samples and relies on rounding, dither and IIR behavior.

Correctness findings discovered while investigating speed
--------------------------------------------------------
A. Existing float serializer mishandles subnormal values.
   Direct writer inputs include +0, -0, minimum/maximum subnormal, minimum
   normal and +/-0.5. The baseline turns bit pattern 0x00000001 into 0x75000000
   instead of retaining a tiny value; its frexp-based normal-number exponent
   construction does not implement subnormals. The maximal subnormal is also
   encoded incorrectly. Signed zero is canonicalized to +0 by the baseline;
   the native prototype deliberately preserves that convention.
   Input/output byte sequences are in conversion-performance.json.

B. Existing 88.2kHz filter can produce non-finite output.
   The random kernel-state probe produces 8456 non-finite intermediate values
   for this coefficient set in both scalar and pair implementations. Other
   tested coefficient sets remain finite. This is a baseline defect, independent
   of the optimization. A public AnalyzeSamples() probe with 10240 frames of a
   440Hz, amplitude-0.2 stereo tone confirms undefined float-to-int conversion
   in the loudness histogram when its logarithm becomes NaN. UBSan reports this
   at gain_analysis.c:599; the probe is included in check_filter_equivalence.py.
   The coefficient/state cause still needs investigation; no replacement
   coefficients are guessed here. This issue must be distinguished from normal
   tiny contraction differences when judging SIMD equivalence.

Recommended next implementation order
------------------------------------
1. Fix/test subnormal float output and validate 88.2kHz analysis correctness.
2. Introduce a paired stereo filter with explicit numerical semantics, a scalar
   fallback and tests across rates, chunk boundaries, quiet/noisy/impulse audio
   and ReplayGain histogram boundaries. Retest arm64 and x86_64.
3. Add native float serialization with endian/property guards and signed-zero
   handling; then reuse buffers as a low-risk structural improvement.
4. Profile shaping kernels and specialize the common no-dither path. Treat any
   RNG/rounding changes as separate behavior changes.
5. Recheck compiler options and cold/storage-bound large Wave64 files.

Reproduction
------------
  python3 tools/benchmark_conversion.py --seconds 60 --repeats 5 \
      --output /tmp/conversion-performance.json
  python3 tools/check_filter_equivalence.py \
      --output /tmp/conversion-filter-equivalence.json

Optional benchmark arguments: --cc selects a compiler; --keep-builds retains
reviewable temporary source variants; --fp-contract-off evaluates the same
workloads with contraction disabled. The default host IEEE/little-endian float
prototype is intentional and is not a portable production implementation.
The benchmark uses generated audio only and does not overwrite user files.
